## Overview

When `NEXT_PUBLIC_DISABLE_SIGNUP` is set to `true`, public registration is blocked for all signup methods. Signup invites let you create accounts for specific email addresses anyway.

The invite flow works like this:

1. An operator calls the internal signup invite API with a shared secret
2. Documenso creates a pending invite and sends an email with a unique link
3. The invitee opens `/signup-invite/{token}` and completes email/password registration
4. The invite is consumed, the email is marked as verified, and the user is signed in automatically

<Callout type="info">
  Invite bypass currently applies to **email/password signup only**. OAuth signup (Google, Microsoft, OIDC) remains blocked when the master signup switch is enabled.
</Callout>

---

## Prerequisites

Before using signup invites, configure:

1. **Email delivery** — Invites are sent by email. See [Email Configuration](/docs/self-hosting/configuration/email).
2. **Database migration** — The `SignupInvite` table must exist. Run pending Prisma migrations after upgrading.
3. **Internal secret** — Set `NEXT_PRIVATE_INTERNAL_SECRET` to enable the internal API (including signup invites).

## Environment Variables

| Variable                               | Required | Default | Description |
| -------------------------------------- | -------- | ------- | ----------- |
| `NEXT_PRIVATE_INTERNAL_SECRET`         | Yes      |         | Shared secret for all `/api/internal/*` endpoints. When unset, internal APIs return `503`. |
| `NEXT_PRIVATE_SIGNUP_INVITE_EXPIRY_DAYS` | No     | `7`     | Default invite lifetime in days (max 30). Can be overridden per invite. |
| `NEXT_PRIVATE_DEFAULT_ORGANISATION_NAME` | No     |         | Default personal organisation display name when not set on the invite |
| `NEXT_PRIVATE_DEFAULT_TEAM_NAME`         | No     |         | Default personal team display name when not set on the invite |
| `NEXT_PUBLIC_DISABLE_SIGNUP`           | No       | `false` | Set to `true` to block public signup. Invited users can still register via email. |

```bash
# Block public signup
NEXT_PUBLIC_DISABLE_SIGNUP="true"

# Enable internal API (signup invites and future /api/internal/* routes)
NEXT_PRIVATE_INTERNAL_SECRET="your-long-random-secret"

# Optional: default expiry (days)
NEXT_PRIVATE_SIGNUP_INVITE_EXPIRY_DAYS="7"

# Optional: default personal org/team names (overridden by per-invite API fields)
NEXT_PRIVATE_DEFAULT_ORGANISATION_NAME="My Organisation"
NEXT_PRIVATE_DEFAULT_TEAM_NAME="My Team"
```

<Callout type="warn">
  Treat `NEXT_PRIVATE_INTERNAL_SECRET` like a root credential. Anyone with this secret can call internal API endpoints, including creating signup invites.
</Callout>

For the full list of signup-related flags, see [Environment Variables — Signup Restrictions](/docs/self-hosting/configuration/environment#signup-restrictions).

## Internal API

All internal endpoints authenticate with `NEXT_PRIVATE_INTERNAL_SECRET`:

```
Authorization: Bearer your-long-random-secret
```

Each endpoint is rate-limited to 30 requests per hour per instance.

<Callout type="info">
  **Invites vs direct provisioning:** Use signup invites when the user should set their own password and signature in the Documenso UI. Use direct user provisioning when your backend must create a fully provisioned account in one call (your app handles sign-in separately via the normal auth API). Use team creation when adding additional property-scoped teams to an existing organisation. Use team API token provisioning to mint `api_...` tokens for v2 API access after a user/team exists.
</Callout>

### Signup Invites

Base path:

```
POST   /api/internal/signup-invites
GET    /api/internal/signup-invites/{token}
DELETE /api/internal/signup-invites/{token}
```

### Create an Invite

`POST /api/internal/signup-invites`

| Field                | Type   | Required | Description |
| -------------------- | ------ | -------- | ----------- |
| `email`              | string | Yes      | Email address to invite (normalized to lowercase) |
| `expiresInDays`      | number | No       | Override default expiry (1–30 days) |
| `organisationName` | string | No       | Display name for the user's personal organisation (applied at signup) |
| `teamName`           | string | No       | Display name for the user's personal team (applied at signup) |

<Tabs items={['curl']}>
<Tab value="curl">
```bash
curl -X POST "https://documenso.example.com/api/internal/signup-invites" \
  -H "Authorization: Bearer your-long-random-secret" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "newuser@example.com",
    "expiresInDays": 7,
    "organisationName": "Acme Corp",
    "teamName": "Legal"
  }'
```
</Tab>
</Tabs>

Example `201` response:

```json
{
  "id": "signup_invite_abc123",
  "email": "newuser@example.com",
  "token": "xYz789AbC",
  "expiresAt": "2025-01-22T10:30:00.000Z",
  "inviteUrl": "https://documenso.example.com/signup-invite/xYz789AbC",
  "organisationName": "Acme Corp",
  "teamName": "Legal",
  "status": "PENDING"
}
```

Creating a new invite for an email address automatically revokes any existing pending invites for that address.

<Callout type="info">
  Organisation and team names are display-only. URL slugs remain auto-generated. When omitted, names fall back to `NEXT_PRIVATE_DEFAULT_ORGANISATION_NAME` / `NEXT_PRIVATE_DEFAULT_TEAM_NAME`, then the built-in defaults (`Personal Organisation`, `Personal Team`).
</Callout>

### Get an Invite

`GET /api/internal/signup-invites/{token}`

Returns invite metadata without exposing sensitive signup fields.

<Tab value="curl">

### Direct User Provisioning

`POST /api/internal/users`

Creates a fully provisioned email/password user in one request. Bypasses `NEXT_PUBLIC_DISABLE_SIGNUP`, skips email verification, and does not send a confirmation email. Your application must sign the user in separately (for example via `/api/auth/email-password/signin`).

| Field                | Type   | Required | Description |
| -------------------- | ------ | -------- | ----------- |
| `name`               | string | Yes      | User display name |
| `email`              | string | Yes      | Email address (normalized to lowercase) |
| `password`           | string | Yes      | Must meet the standard Documenso password policy |
| `signature`          | string | Yes      | Initial user signature (typed or image data) |
| `organisationName` | string | No       | Display name for the user's personal organisation |
| `teamName`           | string | No       | Display name for the user's personal team |

<Tabs items={['curl']}>
<Tab value="curl">
```bash
curl -X POST "https://documenso.example.com/api/internal/users" \
  -H "Authorization: Bearer your-long-random-secret" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Jane Doe",
    "email": "jane@example.com",
    "password": "SecurePass123!",
    "signature": "Jane Doe",
    "organisationName": "Acme Corp",
    "teamName": "Legal"
  }'
```
</Tab>
</Tabs>

Example `201` response:

```json
{
  "userId": 42,
  "email": "jane@example.com",
  "orgUrl": "org_abc123",
  "teamUrl": "personal_xyz789"
}
```

| Status | Meaning |
| ------ | ------- |
| `201`  | User created |
| `400`  | Validation error (weak password, missing signature, disposable email) |
| `401`  | Invalid or missing secret |
| `409`  | Email already registered |
| `503`  | `NEXT_PRIVATE_INTERNAL_SECRET` is not configured |

### Organisation Team Provisioning

`POST /api/internal/organisations/{orgUrl}/teams`

Creates an additional team under an existing organisation. Use after the user account exists — for example when connecting a second property in an external app. The `userId` must belong to a member who can manage the organisation (typically the org owner).

| Field      | Type   | Required | Description |
| ---------- | ------ | -------- | ----------- |
| `teamName` | string | Yes      | Display name for the team (e.g. property name) |
| `userId`   | number | Yes      | Documenso user id with permission to create teams in the org |
| `teamUrl`  | string | No       | URL slug for the team; auto-generated from `teamName` when omitted |

<Tabs items={['curl']}>
<Tab value="curl">
```bash
curl -X POST "https://documenso.example.com/api/internal/organisations/org_abc123/teams" \
  -H "Authorization: Bearer your-long-random-secret" \
  -H "Content-Type: application/json" \
  -d '{
    "teamName": "Oak Street Duplex",
    "userId": 42
  }'
```
</Tab>
</Tabs>

Example `201` response:

```json
{
  "teamId": 84,
  "teamUrl": "oak_street_duplex_a1b2",
  "organisationId": "org_abc123uuid"
}
```

| Status | Meaning |
| ------ | ------- |
| `201`  | Team created |
| `400`  | Invalid body, invalid team URL, or plan team limit exceeded |
| `401`  | Invalid or missing secret |
| `404`  | Organisation not found or user cannot manage it |
| `409`  | Team URL already exists |
| `503`  | `NEXT_PRIVATE_INTERNAL_SECRET` is not configured |

### Team API Token Provisioning

`POST /api/internal/teams/{teamUrl}/api-tokens`

Creates a team API token in one request. The plaintext token is returned **once** in the response — store it immediately. Use the token as `Authorization: Bearer api_...` for v2 API calls (webhooks, envelopes, etc.).

Typical flow:

1. `POST /api/internal/users` → get `teamUrl`, `userId`, and `orgUrl` (first property / account)
2. `POST /api/internal/organisations/{orgUrl}/teams` → get a new `teamUrl` for each additional property-scoped team
3. `POST /api/internal/teams/{teamUrl}/api-tokens` → get `api_...` token
4. Call v2 endpoints with the team API token

| Field              | Type    | Required | Description |
| ------------------ | ------- | -------- | ----------- |
| `tokenName`        | string  | Yes      | Display name for the token |
| `expirationDate`   | string  | No       | `ONE_WEEK`, `ONE_MONTH`, `THREE_MONTHS`, `SIX_MONTHS`, `ONE_YEAR`, or omit/`null` for never |
| `userId`           | number  | No       | Associate token with a team member; omit to use org-owner fallback at API call time |

<Tabs items={['curl']}>
<Tab value="curl">
```bash
curl -X POST "https://documenso.example.com/api/internal/teams/personal_xyz789/api-tokens" \
  -H "Authorization: Bearer your-long-random-secret" \
  -H "Content-Type: application/json" \
  -d '{
    "tokenName": "Acme Integration",
    "expirationDate": "ONE_YEAR",
    "userId": 42
  }'
```
</Tab>
</Tabs>

Example `201` response:

```json
{
  "id": 7,
  "token": "api_xxxxxxxxxxxxxxxx",
  "teamId": 42,
  "teamUrl": "personal_xyz789",
  "expiresAt": "2026-06-04T12:00:00.000Z"
}
```

| Status | Meaning |
| ------ | ------- |
| `201`  | Token created (plaintext shown once) |
| `400`  | Invalid body, invalid expiration, or user not on team |
| `401`  | Invalid or missing secret |
| `404`  | Team not found |
| `503`  | `NEXT_PRIVATE_INTERNAL_SECRET` is not configured |

### Team API Token Deletion

`DELETE /api/internal/teams/{teamUrl}/api-tokens/{tokenId}`

Deletes a team API token created via the internal provisioning API. Use during integration disconnect cleanup after webhook removal.

<Tabs items={['curl']}>
<Tab value="curl">
```bash
curl -X DELETE "https://documenso.example.com/api/internal/teams/personal_xyz789/api-tokens/7" \
  -H "Authorization: Bearer your-long-random-secret"
```
</Tab>
</Tabs>

| Status | Meaning |
| ------ | ------- |
| `204`  | Token deleted |
| `400`  | Invalid token ID |
| `401`  | Invalid or missing secret |
| `404`  | Team or token not found |
| `503`  | `NEXT_PRIVATE_INTERNAL_SECRET` is not configured |

<Callout type="warn">
  Treat API tokens like passwords. Anyone with the plaintext `api_...` value can act on behalf of the team. Tokens created without `userId` fall back to the organisation owner when used for v2 API calls.
</Callout>

## Invite Page

Invited users open the link from their email:

```
https://documenso.example.com/signup-invite/{token}
```

The page shows invite details and a signup form with the email field locked to the invited address. Possible states:

| Status    | What the user sees |
| --------- | ------------------ |
| `PENDING` | Invite details and signup form |
| Expired   | "Invitation expired" message |
| `REVOKED` | "Invitation revoked" message |
| Accepted  | Redirect or confirmation that the invite was already used |

After successful registration, the invite is marked as accepted and the token cannot be reused. Invited users skip the email verification step — the invite link serves as proof of email ownership — and are signed in automatically after creating their account.

<Callout type="info">
  Regular public signup still requires email verification. Only users who register through a valid invite link bypass `/unverified-account`.
</Callout>

## Error Responses

| Status | Meaning |
| ------ | ------- |
| `401`  | Missing or invalid `Authorization` header |
| `503`  | `NEXT_PRIVATE_INTERNAL_SECRET` is not configured |
| `404`  | Invite token not found |
| `400`  | Invite already accepted or cannot be revoked |
| `429`  | Rate limit exceeded (30 requests per hour) |

During signup, invalid or expired invites return application errors with codes `SIGNUP_INVITE_INVALID` or `SIGNUP_INVITE_EXPIRED`.
